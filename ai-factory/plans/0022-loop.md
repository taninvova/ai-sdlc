# /fc:loop — run every step of a plan until done

**Goal:** Add `/fc:loop <plan>`. It implements every unticked step of one plan in one invocation and runs ready steps concurrently in temporary git worktrees on Claude Code. It applies each step's delta back to the main tree uncommitted, then ends with one `/fc:check`. Headless runs get fixed exit codes.

**Spec:** [`ai-factory/specs/0022-loop.md`](../specs/0022-loop.md). This plan covers the spec as written: numeric `NNNN` plan selection only (AC1–AC4). Accepting spec 0024's letter-and-digit IDs is out of scope until the spec is amended (see Ambiguity 1).

## Design

- **A helper owns every deterministic decision. The prompt only orchestrates.**
  - The new `skills/ai-layout/templates/ai-factory/make/loop.js` (CommonJS, stdlib only) owns:
    - option parsing;
    - plan selection;
    - the step grammar and `Depends on:`;
    - validation and scheduling;
    - worktree snapshot and apply-back;
    - ticking after an apply;
    - stop causes, the report and the exit code.
  - The task prompt `tasks/loop.md` starts implementers, waits for them, enforces the timeout on Claude Code, and passes their results to the helper.
  - The workspace root is resolved from `process.argv[1]`, as in `assurance.js` and `contracts.js`, so this repo's symlink works.
- **Subcommands.** Every subcommand prints one JSON object on stdout, and module exports are the test seam.

  | Subcommand | What it does |
  |---|---|
  | `start <arg> [--max-parallel N] [--step-timeout M] [--host claude\|codex\|headless]` | Parses the options, selects the plan, validates it, then creates the loop state under `ai-factory/runs/tmp/loop/<loop-id>/state.json` |
  | `next <loop-id>` | Returns the steps to start now, each with its mode (`main` or `worktree`), or `wait`, `check` or `stop` |
  | `prepare <loop-id> <step>` | Creates a worktree and copies the snapshot into it |
  | `finish <loop-id> <step> --result met\|failed\|timeout` | Records the step's result. For a worktree step it then makes the two commits and applies the delta back in plan order |
  | `verdict <loop-id>` | Reads the reviewer JSON on stdin |
  | `end <loop-id>` | Prints the report and writes the outcome record |

- **Step grammar** is reused, not copied. It comes from `require("./contracts.js").parsePlanSteps`, which is already exported and documented as state.sh's grammar. `contracts.js` itself is not edited.
- **The `Depends on:` line.**
  - It sits in a step's indented continuation body, exactly `Depends on: N[, M…]`, with numbers only.
  - A step without the line depends on every earlier step.
  - Validation reports:
    - a missing reference, naming the step and the number;
    - a cycle, naming the steps in it;
    - an unticked step that carries a withdrawn record.

    Duplicates within a line are tolerated.
- **Exit codes of `loop.js start`.** Usage 2, validation 3, and candidate listing 0 with no state created. A usage error is decided before the plan is read (AC5, AC6).
- **Candidate listing (AC2–AC4).**
  - The rows use the `--plans` table of `skills/ai-layout/scripts/state.sh` (header plus `kind number state path step detail`).
  - `loop.js` builds the rows itself, because a workspace helper cannot assume the plugin path in a headless run.
  - Parity is a test, `select-parity-with-state`. It runs `state.sh --plans` on the same fixture and compares the bytes, so 0024's header rename to `id` reaches the loop without a second edit (see Risks).
- **Scheduling rule.** These follow from AC14–AC17 and AC21–AC23:
  - A step is ready when every step it depends on is ticked in the main tree.
  - Ready steps start in plan order, up to `--max-parallel`, which defaults to 3.
  - A step runs in the main tree only if no other step is running and it is the only one starting. Otherwise it runs in a worktree.
  - While a main-tree step runs, nothing else can become ready, because nothing else finishes. So the two modes never overlap.
  - On Codex (`--host codex`), the effective limit is 1 and the report carries a `sequential on Codex` note (AC34). `--step-timeout` is recorded as `not enforced on Codex` (AC65, AC66).
- **Apply order (AC30).** A finished worktree step is applied only after every lower-numbered step that is still running has finished. Its delta waits in a queue keyed by step number (see Ambiguity 4).
- **Snapshot (AC25).**
  1. `git diff --binary HEAD` is applied in the new worktree.
  2. `git ls-files --others --exclude-standard -z` files are copied in.
  3. Worktrees are created with `git worktree add -b fc-loop/<loop-id>/S<N> ai-factory/runs/tmp/worktrees/<loop-id>-S<N> HEAD`.

  Any failure is recorded as a `snapshot` cause, and that step does not start (AC26).
- **Commits in the worktree only (AC28).**
  - The baseline commit holds the snapshot. The step commit sits on top and holds the implementer's changes.
  - Both use `git -c user.name=fc-loop -c user.email=fc-loop@invalid -c commit.gpgsign=false commit --no-verify --allow-empty`. That way the developer's hooks and signing never run, and an empty step still yields two commits.
  - The helper never runs `commit`, `reset`, `checkout`, `stash` or `update-ref` in the main tree. Tests assert `HEAD` and the branch list (AC32, AC33).
- **Apply-back (AC29, AC62–AC64, AC43, AC70).**
  1. `git diff --binary <baseline>..<step>` goes to `git apply --check` on the main tree.
  2. If the check is clean, the helper runs plain `git apply`.
  3. If it fails, the helper runs `git apply --3way`:
     - conflict markers mean `conflict`, and the helper lists the conflicted files;
     - a refusal with no markers means `refused`, and the helper lists the touched files, with the index and working files unchanged.
  4. After a clean apply, `loop.js` ticks `- [ ] Step N` to `- [x]` in the main tree's plan (AC31), deletes the branch and removes the worktree.
  5. Plan-file edits made by the implementer in worktree mode are excluded from the delta: `-- . ':!<plan path>'`. Only the loop ticks.
- **Outcome.**
  - Causes are appended in the order they happen, each naming its step. The kinds are `failed`, `timeout`, `snapshot`, `conflict`, `refused` and `verdict`.
  - Exit priority is 4 (conflict, refused, snapshot), then 1 (failed, timeout), then 5 (verdict, only with `GATE_ENFORCE=1`), else 0. Usage 2 and validation 3 come only from `start` (AC67–AC69).
  - `verdict` applies `gate.js` `parseVerdict` semantics: a valid `approve` with no blocker counts as approval.
  - The outcome record goes to `$FC_LOOP_RESULT` when the runner set that variable. Otherwise it goes to `ai-factory/runs/tmp/loop/<loop-id>/outcome.json`.
- **Headless.**
  - `runner.js` treats `TASK=loop` specially:
    - **Before launch:** it runs `loop.js start` in-process on `INPUT`. Usage exits 2 and validation exits 3, with no host launched and no run file written. A listing is printed, the run exits 0 and nothing launches.
    - **During the run:** it passes the loop ID and `FC_LOOP_RESULT` to the child.
    - **After the child exits:** it reads the outcome record and sets `process.exitCode`. A missing or unreadable record exits 1 and says so.
  - GNU make turns every non-zero recipe status into its own exit status of 2 (see Ambiguity 2).
- **Hooks in a worktree.**
  - `_common.js` gains `logDir(ev)`. It returns the main repository's layout directory, found from `git rev-parse --git-common-dir` run in the event's cwd. Every log and lifecycle writer uses it (AC37).
  - `aiDir()` keeps its meaning for the guard.
  - `guard-paths.js` handles a target that, relative to the main root, lies under `<layout>/runs/tmp/worktrees/<name>/`:
    - it matches the remainder against `dont-touch.md` as if relative to the worktree root, and blocks or allows on that (AC35);
    - every other path under `runs/` is still blocked (AC36).
  - Nothing under `runs/tmp/worktrees/` is scanned or collected (AC38).
- **Session ownership.** `loop` is session-owned, like `continue`:
  - `models.js` never routes it to a worker, because a routed worker may not delegate and could not run implementers in parallel;
  - `routing.tasks.loop` produces a doctor finding;
  - each step's delegation is the `run` task's (see Ambiguity 6).

## Server versus client

N/A. This is a plugin of prompts, local Node helpers and bash checks, with no application, UI or service. The deterministic parts (options, scheduling, git operations, exit codes) live in `loop.js` and `runner.js`. Concurrent delegation and the host timeout live in the session that runs `tasks/loop.md`.

## Ambiguities in the spec

1. **New-style IDs.** Per the spec's note and its Out of scope section, selection accepts numeric `NNNN` only. Plan files that 0024 creates with letter-and-digit IDs cannot be selected until the amendment. A path argument to such a file is refused as "unknown plan" rather than accepted.
2. **Headless exit codes through `make`.** GNU make exits 2 for any failing recipe; this was verified locally with `exit 3` giving status 2. So `make ai TASK=loop` cannot itself exit 1, 3, 4 or 5 as AC47–AC52 and AC67–AC68 say, and its 2 is indistinguishable from usage. The plan makes `node ai-factory/make/runner.js ai` (with `TASK=loop`) return the exact codes, asserts them there, and documents the `make` caveat. **The developer must decide** whether that satisfies the ACs, or whether a different headless entry, such as a documented direct `node` invocation, becomes the contract.
3. **"Candidate plans" (AC2, AC3).** The plan lists the outstanding plans' rows in `state.sh --plans` form. AC2 and AC3 do not say whether finished plans (`plans/done/`) are candidates. It also does not say whether AC4's "matching plans" use the same table; the plan uses the same table for both.
4. **"Plan order" for overlapping batches (AC30).** The plan holds a finished step until every lower-numbered running step has finished. That is the strict reading. It can delay a dependent step's start.
5. **Contract evidence for worktree steps (AC60).** The spec says "the same evidence a `/fc:run` records". The plan records it in the main tree after the apply, not in the worktree. That is outside AC57's single implementer line: the delegation tells the implementer not to record evidence in worktree mode.
6. **Model routing for `loop`.** The spec lists "`models.yaml` / `models.js`: a `loop` task entry" but gives no rule. The plan makes `loop` session-owned, like `continue`, because a routed worker may not delegate. Per-step delegation follows the `run` task's policy.
7. **"The guard hook's scans" (AC38).** The guard reads only its target paths and does no directory scan. The plan reads AC38 as "the guard never treats the subtree as main-repo paths, and no hook enumerates it".
8. **AC39 versus the existing ignore.** `ai-factory/.gitignore` already has `/runs/tmp/`. The plan still adds `ai-factory/runs/tmp/` to the root `.gitignore`, as the AC reads literally.
9. **The ADR step runs under `/fc:adr`, not `/fc:run`.** The architect owns `ai-factory/adr/`. The developer ticks Step 1 after the ADR exists and its check passes.
