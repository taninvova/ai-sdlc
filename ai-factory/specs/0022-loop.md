# 0022 — /t4:loop: run every step of a plan until done

`/t4:loop <plan>` implements every unticked step of one plan. When two or more steps are ready, they run concurrently, each in its own git worktree, and their deltas are applied back to the main tree uncommitted. `/t4:check` runs at the end.

Status: ready for planning. The developer's answers from five interview rounds are recorded below, and no open questions remain.

> **Note — sequencing with spec 0024.** Spec 0024 (letter-and-digit IDs) is being implemented now and ships first. This spec will then be amended so that `/t4:loop` also accepts the new-style IDs. Until that amendment, the plan-selection criteria below (AC1–AC4) describe the current numeric `NNNN` form only.

## User story

As a developer with a written plan, I want one command that runs every remaining step of that plan until it is done, running independent steps in parallel, so that I do not have to invoke `/t4:run` once for each step and wait between them.

## Request (verbatim)

> create a command to run all steps of a plan in a loop till done. run in parallel in possible

## Decisions from the developer (interview)

Where a later answer replaces an earlier one, only the later one is kept.

1. **Halt rule.** A new ADR records `/t4:loop` as an explicit opt-in exception to DEC-003, BR-010 and FR-026 (analysis 0001). `/t4:run` still halts after one step. `docs/workflow.md` and `AGENTS.md` name the exception.
2. **Commit rule.** Nothing is ever committed on the developer's branch. Commits exist only on temporary branches inside the loop's worktrees, and the ADR records them as the only exception to FR-027.
3. **Command.** `/t4:loop <plan>`, with the plan given by number or by path. If there is no argument, the plan is unknown or the argument matches several plans, the loop lists the candidates the way `/t4:state` does and stops.
4. **Options.**
   - `--max-parallel` is an integer from 1 to 8, with a default of 3.
   - `--step-timeout` is an integer number of minutes from 1 to 240, with a default of 30, and it applies to all steps.
   - Any other value is a usage error.
   - There is no per-step timeout override in the plan, no total step cap and no cost cap.
5. **Dependencies.** A step may carry `Depends on: N, M`, which the planner fills in, and may start once every listed step is ticked. A step without the line depends on all earlier steps. The whole plan is validated before any step starts, for missing references, cycles and withdrawn-but-unticked steps, and on any problem the loop stops and asks (headless: reports and stops).
6. **Worktrees.**
   - A worktree is used only when two or more steps run concurrently. A step running alone runs in the main tree and ticks exactly as under `/t4:run`.
   - Worktrees live under `ai-factory/runs/tmp/worktrees/` and branch from `HEAD`.
   - Each worktree gets a snapshot of the main tree first: `git diff --binary HEAD` plus untracked, non-ignored files. Staging state is not preserved.
   - If the snapshot fails to apply, the loop stops before that step starts.
7. **Merge-back.**
   - In the worktree, after the implementer returns, the loop commits the snapshot as a baseline commit and then the step's work as a second commit on top.
   - It takes `git diff --binary <baseline>..<step>` and runs `git apply --check` on the main tree first. If the check is clean, it applies the diff with plain `git apply`, which changes the working tree only and leaves staging untouched.
   - If the check fails, it falls back to `git apply --3way`. Staging changes only in this fallback, and the report says so.
   - If the fallback leaves conflicts, or refuses without writing conflict markers (unstaged changes in a touched main-tree file, or missing blobs), that is a conflict, handled like a failure: no new step starts, running steps finish and apply back, the loop stops, keeps the worktree and reports its path and the files with conflict markers.
   - After a clean apply, the loop ticks the step in the main tree. The result is never committed.
8. **Implementer.** `agents/implementer.md` gains one line: in worktree mode, do not tick, and report the phase result.
9. **Failure.** A failure is a step left unticked, a phase not met, or a timeout. On a failure the loop starts no new step, lets in-flight steps finish and merge back, then stops and reports the failed step, its output and the remaining steps.
   - On a timeout, the loop stops the implementer. A worktree step keeps its worktree, and the report gives its path. A main-tree step's partial changes are left in place and reported.
   - A failed snapshot copy into a new worktree is handled the same way: no new step starts, running steps finish and apply back, then the loop stops and reports the failed copy.
10. **Safeguards.**
    - This repo's `.gitignore` ignores `ai-factory/runs/tmp/`.
    - Hooks that fire inside a worktree write their logs and lifecycle events to the main repo's `ai-factory/runs/`, resolved through the git common dir.
    - `/t4:check` and the guard hook's scans skip `runs/tmp/worktrees/`. The guard allows edits inside that subtree, with dont-touch rules applied relative to the worktree's root.
    - The docs state that test tools must exclude that subtree.
11. **End of loop.** After the last step is ticked, the loop runs `/t4:check` and includes its verdict. It does the same when the plan was already fully ticked, changing no files. It does not run `/t4:test gaps`.
12. **Runtimes.** On Codex, steps always run one at a time, `--max-parallel` is accepted, and the report says the steps ran sequentially. `--step-timeout` is accepted but not enforced on Codex, and the report says so. Headless `make ai TASK=loop` is supported.
13. **Headless exit codes.** These codes are the contract of `node ai-factory/make/runner.js ai TASK=loop …`.
    - 1: step failure or timeout.
    - 2: usage error.
    - 3: plan validation failure.
    - 4: merge conflict or failed worktree snapshot copy.
    - 5: review verdict other than `approve` with `GATE_ENFORCE=1`. Without it, the verdict does not affect the exit code.
    - If a run hits several causes, a fixed priority picks the exit code: 4, then 1, then 5. Usage (2) and validation (3) happen before any step runs, so they never combine with the others. The report lists every cause in the order it happened.
    - GNU make exits 2 whenever a recipe fails, so `make ai TASK=loop` cannot pass these codes through. It returns 0 on success and 2 on any failure, and the documentation states this limitation (decided during planning).
14. **Opt-in features.**
    - Each step behaves like a `/t4:run` for lifecycle, assurance and contract evidence.
    - The loop wraps everything in one run with phase `loop`. Each step's run and the in-loop `check` run carry `--parent-run <loop run>`.
    - `/t4:continue` resumes a stopped loop's plan one step at a time.

## Acceptance criteria

### Invocation and options

- **AC1** Given a plan that exists in `ai-factory/plans/`, When the developer runs `/t4:loop <NNNN>` or `/t4:loop <path to that plan>`, Then the loop runs on that plan. Both forms select the same plan.
- **AC2** Given `/t4:loop` with no argument, When it runs, Then it lists the candidate plans in the format `/t4:state` uses, implements no step, changes no file and stops.
- **AC3** Given `/t4:loop <arg>` where `<arg>` matches no plan, When it runs, Then it lists the candidate plans in the format `/t4:state` uses, implements no step, changes no file and stops.
- **AC4** Given `/t4:loop <arg>` where `<arg>` matches two or more plans, When it runs, Then it lists the matching plans, implements no step, changes no file and stops.
- **AC5** Given `--max-parallel` with a value that is not an integer from 1 to 8, When the loop starts, Then it reports the option's usage and stops before it validates the plan or runs any step, and no file changes.
- **AC6** Given `--step-timeout` with a value that is not an integer from 1 to 240, When the loop starts, Then it reports the option's usage and stops before it validates the plan or runs any step, and no file changes.
- **AC7** Given `--max-parallel 1`, When the loop runs a plan whose steps could run in parallel, Then every step runs one at a time in the main tree, in plan order, and no worktree is created.

### Plan validation, before any step runs

- **AC8** Given a plan where a step's `Depends on:` names a step number that does not exist in the plan, When the loop starts, Then it runs no step, changes no file, names the step and the missing reference, and stops.
- **AC9** Given a plan whose `Depends on:` lines form a cycle, When the loop starts, Then it runs no step, changes no file, names the steps in the cycle, and stops.
- **AC10** Given a plan with any step that is unticked but carries a `**Result — Step N withdrawn; …**` record, wherever it sits in the plan, When the loop starts, Then it runs no step, changes no file, and asks the developer to reconcile the plan.
- **AC11** Given headless `node ai-factory/make/runner.js ai TASK=loop …` and a plan that fails AC8, AC9 or AC10, When it runs, Then it asks no question, reports the problem, runs no step and exits with code 3.

### Running until done

- **AC12** Given a plan with two or more unticked steps and no failure, When `/t4:loop` runs on it, Then every unticked step is implemented and ticked in that one invocation, with no further command from the developer between steps.
- **AC13** Given the loop runs a step, When it is implemented, Then the work is delegated to the `implementer` agent under that step's own verification phase (`red`, `step` or `final`). The loop itself writes no implementation.
- **AC14** Given a step with no `Depends on:` line, When the loop schedules it, Then it starts only after every earlier step in the plan is ticked, and no later step starts before it is ticked.
- **AC15** Given a plan written before this feature, which has no `Depends on:` lines, When `/t4:loop` runs on it, Then every step runs one at a time in the main tree, in plan order, and no worktree is created.
- **AC16** Given a step with `Depends on: N, M`, When the loop schedules it, Then it does not start before steps N and M are both ticked in the main tree.
- **AC17** Given a step that runs with no other step running at the same time, When it is implemented, Then it runs in the main tree, not in a worktree, and its checkbox is ticked exactly as `/t4:run` would tick it.
- **AC18** Given the last unticked step has been ticked, When the steps are finished, Then the loop runs `/t4:check` once, and its report includes the reviewer's verdict unchanged, together with the steps run in this invocation.
- **AC19** Given a plan with every step already ticked, When `/t4:loop` runs on it, Then it implements no step and changes no file, runs `/t4:check` once, and reports that no steps remained, together with the verdict.
- **AC20** Given the loop has finished, When it completes, Then it has not run `/t4:test gaps`.

### Parallel steps and worktrees

- **AC21** Given two or more unticked steps whose `Depends on:` steps are all ticked, When the loop reaches them on Claude Code, Then it starts them concurrently, up to the parallel limit.
- **AC22** Given no `--max-parallel` option, When more than three steps are ready, Then no more than three run at the same time.
- **AC23** Given `--max-parallel N` with N from 2 to 8, When more than N steps are ready, Then no more than N run at the same time.
- **AC24** Given two or more steps start concurrently, When each starts, Then each runs in its own git worktree under `ai-factory/runs/tmp/worktrees/`, on its own temporary branch created from `HEAD`.
- **AC25** Given the main tree has staged changes, unstaged changes, deletions, binary changes or untracked files that are not ignored, When a worktree is created for a step, Then all of them are present in the worktree's files before the implementer starts. Ignored files are not copied, and whether a change was staged is not carried over.
- **AC26** Given the main tree's snapshot fails to apply to a new worktree, When the loop detects it, Then that step does not start, no further step starts, and steps already running finish and are brought back as in AC29 and AC30. The loop then stops, and its report names the step whose snapshot copy failed.
- **AC27** Given the loop delegates a step that runs in a worktree, When it delegates, Then the delegation says worktree mode, and the implementer reports its phase result without ticking the step's checkbox.
- **AC28** Given a worktree step's implementer has returned with its phase met, When the loop records the result, Then the worktree's temporary branch has exactly two new commits made by the loop: a baseline commit holding the snapshot of AC25, and a step commit on top holding the implementer's changes.
- **AC29** Given a worktree step's two commits exist, When the loop brings the result back, Then it runs `git apply --check` with `git diff --binary <baseline>..<step>` against the main tree. If the check passes, it applies the diff with plain `git apply`: the working tree gains only that step's own changes, not the snapshot a second time, the index (staging) is unchanged, and nothing is committed.
- **AC30** Given parallel steps have finished cleanly, When their results are brought back, Then they are applied in plan order, whatever order they finished in.
- **AC31** Given a worktree step's delta applied cleanly, When the loop continues, Then it ticks that step in the main tree's plan, deletes the temporary branch and removes the worktree.
- **AC32** Given any run of the loop, When it ends, Then the developer's branch has no new commit, `HEAD` is where it was when the loop started, and the main tree's changes from before the loop are still present.
- **AC33** Given any run of the loop, When it ends, Then the main working tree has not been reset.
- **AC34** Given the loop runs on Codex and two or more steps are ready, When it reaches them, Then it runs them one at a time in plan order in the main tree, and the report states that parallel steps ran sequentially on Codex, whether or not `--max-parallel` was given.

### Hooks and tools around worktrees

- **AC35** Given an implementer in a loop worktree edits a file inside `ai-factory/runs/tmp/worktrees/<worktree>/`, When the guard hook checks it, Then it allows the edit, unless the path relative to the worktree's root matches a `dont-touch.md` rule, in which case it blocks it.
- **AC36** Given the feature is delivered, When the guard hook receives an edit under `ai-factory/runs/` outside `ai-factory/runs/tmp/worktrees/`, Then it still blocks it.
- **AC37** Given a hook fires inside a loop worktree, When it writes a run-log row, a task marker or a lifecycle event, Then the write lands in the main repository's `ai-factory/runs/`, found through the git common dir, and not in the worktree's own `ai-factory/runs/`.
- **AC38** Given `ai-factory/runs/tmp/worktrees/` holds one or more worktrees, When `/t4:check` collects the change to review, or the guard hook scans paths, Then nothing under `ai-factory/runs/tmp/worktrees/` is included.
- **AC39** Given the feature is delivered, When this repo's `.gitignore` is read, Then it ignores `ai-factory/runs/tmp/`.
- **AC40** Given the feature is delivered, When `docs/workflow.md` (or the `/t4:loop` documentation) is read, Then it states that test, lint and typecheck tools must exclude `ai-factory/runs/tmp/worktrees/`.

### Failure, conflict and timeout

- **AC41** Given a step ends unticked or with its verification phase not met, When the loop learns of it, Then it starts no further step, waits for the steps already running to finish, brings back those that finished cleanly as in AC29 and AC30, and stops.
- **AC42** Given the loop stopped under AC41, When it reports, Then the report names the failed step, relays that step's output and lists the steps still unticked. If the failed step ran in a worktree, the report gives the worktree's path, and the worktree still exists.
- **AC43** Given `git apply --check` fails for a step's delta and the `git apply --3way` fallback (AC63) leaves conflicts, When the loop detects it, Then it treats this as a conflict: it does not tick that step, starts no new step, lets steps already running finish and come back as in AC29 and AC30, keeps the conflicting step's worktree, and stops. The report names the step, lists the main-tree files left with conflict markers (or, for a refused apply, the touched files, as in AC70) and gives the worktree's path.
- **AC44** Given the loop runs on Claude Code and a step runs longer than its timeout (30 minutes, or `--step-timeout`), When the timeout passes, Then the loop stops that implementer, treats the step as failed, and AC41 and AC42 apply.
- **AC45** Given a step that ran in the main tree timed out, When the loop reports, Then the step's partial changes are still in the main tree, and the report says they are partial and lists the files changed.
- **AC46** Given a plan of any length, When the loop runs, Then it does not stop because of a total step count or a cost limit.

### Headless

- **AC47** Given headless `node ai-factory/make/runner.js ai TASK=loop …` and a step that fails or times out, When the loop stops, Then it asks no question, reports as in AC42 and exits with code 1.
- **AC48** Given headless `node ai-factory/make/runner.js ai TASK=loop …` and a conflict under AC43, or a failed snapshot copy under AC26, When the loop stops, Then it asks no question and exits with code 4.
- **AC49** Given headless `node ai-factory/make/runner.js ai TASK=loop …` and a usage error under AC5 or AC6, When it stops, Then it exits with code 2.
- **AC50** Given headless `node ai-factory/make/runner.js ai TASK=loop …` and every step ticked with no failure, When `/t4:check` returns a valid `approve` with no blockers, Then the run exits with code 0.
- **AC51** Given headless `node ai-factory/make/runner.js ai TASK=loop …` with `GATE_ENFORCE=1`, When the steps finish and `/t4:check` returns anything but a valid `approve` with no blockers, Then the run exits with code 5.
- **AC52** Given headless `node ai-factory/make/runner.js ai TASK=loop …` without `GATE_ENFORCE=1`, When the steps finish and `/t4:check` returns a verdict other than `approve`, Then the run exits with code 0 and reports the verdict.

### Halt rule, commit rule and documentation

- **AC53** Given the feature is delivered, When `ai-factory/adr/` is read, Then a new ADR records `/t4:loop` as an explicit opt-in exception to DEC-003, BR-010 and FR-026, and records that commits on the loop's temporary worktree branches are the only exception to FR-027.
- **AC54** Given the feature is delivered, When `/t4:run <plan> <step>` runs, Then it still implements exactly one step and halts, unchanged.
- **AC55** Given the feature is delivered, When `ai-factory/docs/workflow.md` ("The rules that make it work") and `ai-factory/AGENTS.md` are read, Then both name `/t4:loop` as the exception to "one step per `/t4:run`", and `AGENTS.md` lists `/t4:loop` among the slash commands.

### Planner, plan format and implementer

- **AC56** Given the feature is delivered, When the plan template (`tasks/plan.md`) and the planner are read, Then they define an optional per-step line `Depends on: N, M`, state that a step without it waits for all earlier steps, and instruct the planner to write it where steps are independent, referring only to existing earlier step numbers and never forming a cycle.
- **AC57** Given the feature is delivered, When `agents/implementer.md` is read, Then it has a line saying that when the delegation says worktree mode, the implementer does not tick the step and reports the phase result. Outside worktree mode its behaviour is unchanged.

### Opt-in features

- **AC58** Given lifecycle telemetry is enabled, When the loop runs, Then it opens and closes one run with phase `loop`. Each step opens and closes its own `run` lifecycle run with `--step S<N>` and `--parent-run <loop run>`, and the in-loop `/t4:check` opens and closes a run with phase `check` and `--parent-run <loop run>`.
- **AC59** Given `ai-factory/assurance.json` exists, When the loop runs a step, Then that step's assurance requirements are shown and applied exactly as `/t4:run` applies them.
- **AC60** Given artifact contracts are enabled, When the loop runs a step, Then that step records the same contract evidence a `/t4:run` of that step records.
- **AC61** Given a contracts-enabled delivery whose loop stopped with unticked steps, When the developer runs `/t4:continue <delivery id>`, Then it offers the next unticked step as a single `/t4:run` handoff.

### Apply mode (round 4)

- **AC62** Given the main tree has staged changes, When a worktree step's delta passes `git apply --check` and is applied with plain `git apply`, Then the index is the same before and after the apply, and the report does not say staging changed.
- **AC63** Given `git apply --check` fails for a step's delta, When the loop continues, Then it applies the delta with `git apply --3way`. If that leaves no conflicts, it ticks the step as in AC31, and the report states that this step's apply used the `--3way` fallback and changed staging in the main tree.
- **AC64** Given the plain `git apply` path is taken for every step in a run, When the loop ends, Then nothing in its report says staging changed.

### Codex timeout (round 4)

- **AC65** Given the loop runs on Codex with or without `--step-timeout`, When a step runs longer than the timeout, Then the loop does not stop it or treat it as failed for exceeding the timeout, and the report states that the step timeout was not enforced on Codex.
- **AC66** Given the loop runs on Codex with a `--step-timeout` value from 1 to 240, When it starts, Then the option is accepted and is not a usage error.

### Several stop causes in one run (round 5)

- **AC67** Given headless `node ai-factory/make/runner.js ai TASK=loop …` and a run in which a conflict or a failed snapshot copy occurs as well as a step failure or timeout, in either order, When the run stops, Then it exits with code 4.
- **AC68** Given headless `node ai-factory/make/runner.js ai TASK=loop …` with `GATE_ENFORCE=1` and a run in which a step failure or timeout occurs and the review verdict is not `approve`, with no conflict or failed snapshot copy, When the run ends, Then it exits with code 1.
- **AC69** Given a run that hits more than one stop cause, When the loop reports, Then the report lists every cause in the order it happened, each naming its step.

### A `--3way` fallback that refuses (round 5)

- **AC70** Given `git apply --check` fails for a step's delta and `git apply --3way` then refuses without writing conflict markers, because a touched main-tree file has unstaged changes or a needed blob is missing, When the loop detects it, Then it treats this as a conflict under AC43:
  - it does not tick that step and starts no new step
  - steps already running finish and come back as in AC29 and AC30
  - the step's worktree is kept
  - the main tree's working files and index are unchanged by that apply
  - the report says the apply was refused and names the touched files, in place of files with conflict markers
  - in a headless run through `node ai-factory/make/runner.js ai TASK=loop …`, the exit code is 4

### `make ai` exit status (planning decision)

- **AC71** Given headless `make ai TASK=loop INPUT="<plan>"`, When the loop succeeds, Then make exits 0. When the loop ends with any of the causes behind codes 1 to 5, make exits 2. The `/t4:loop` documentation and `docs/workflow.md` state that only `node ai-factory/make/runner.js ai TASK=loop …` returns the distinct codes 1 to 5, and that `make ai TASK=loop` reports every failure as 2.

## Out of scope

- Writing or changing the spec. The loop starts from an existing plan.
- Accepting the letter-and-digit IDs of spec 0024. That comes in a later amendment of this spec.
- Running `/t4:test red`, `/t4:test gaps` or `/t4:report` from inside the loop.
- Any commit on the developer's branch, pushing, or opening an MR.
- Changing `/t4:run`'s one-step behaviour.
- Running more than one plan in one invocation.
- A total step cap or a cost cap, and a per-step timeout override in the plan.
- Parallel execution on Codex.
- Making `/t4:continue` hand off to `/t4:loop`.
- Resolving conflicts automatically, and cleaning up worktrees kept after a failure, conflict or timeout.
- Preserving the main tree's staging state inside worktrees, and preserving it in the main tree when the `--3way` fallback runs.
- Enforcing the step timeout on Codex.

## Data touched

- Plan files `ai-factory/plans/<NNNN>-<slug>.md`:
  - the `- [ ] Step N — …` / `- [x]` checkboxes, ticked by the implementer in the main tree or by the loop after a clean apply
  - the new optional `Depends on: N, M` line
  - the `**Result — Step N withdrawn; …**` records, which are validated
- Git worktrees under `ai-factory/runs/tmp/worktrees/` and their temporary branches, each with a baseline commit and a step commit. Both are removed after a clean apply and kept after a failure, conflict or timeout.
- The main tree's index, which changes only when the `git apply --3way` fallback runs (AC63). The plain `git apply` path leaves it untouched.
- Lifecycle events: a new `loop` phase, and `parent_run_id` set on the per-step `run` events and the in-loop `check` event, all written to the main repo's `ai-factory/runs/`.
- Run log rows and task markers. Their shape is unchanged, they are always written to the main repo, and the new task is recognized as `loop`.
- Artifact contract evidence per step, unchanged in shape.
- This repo's `.gitignore`, which gains `ai-factory/runs/tmp/`.

## Routes touched

None: the plugin has no HTTP surface. The surfaces are the new slash command `/t4:loop` (options `--max-parallel N`, `--step-timeout <minutes>`), its Codex skill, headless `node ai-factory/make/runner.js ai TASK=loop …` with exit codes 0 to 5, and `make ai TASK=loop`, which returns 0 or 2.
